# Практическая №4: реализация на Unity

Проект: **Game_PRMICSS — простая сетевая 3D-демонстрация**. Версия: **Unity 6000.5.0b2**, NGO **2.13.3**, Unity Transport **6.5.0**, Input System **1.19.0**, URP **17.5.0**. Проверка упрощённой версии: **3 ноября 2026**, macOS.

Состав команды / ФИО: не указан пользователем. Хеш коммита: отсутствует, папка не является Git-репозиторием. Контрольные суммы исходников: [source-sha256.txt](source-sha256.txt). Ветки `main`, `feature/prediction` и PR GitVerse здесь не созданы: для них нужен настоящий репозиторий и его адрес.

**Отклонение от методички:** задание требует Unreal Engine и его штатный CharacterMovementComponent. По запросу пользователя выполнена Unity-адаптация, с собственной симуляцией и обработкой вводов. Это функциональная демонстрация сетевых принципов; требования к движку, `ACharacter` и встроенным `SavedMoves` Unreal не выполнены.

## Минимальная сцена и роли

В `Assets/Scenes/Demo.unity` четыре корневых объекта: камера, свет, `NetworkManager`, `DemoWorld` (пол, стена, четыре границы). В меню площадка скрыта, при подключении появляется. Игрок — простой префаб капсулы. Маленькая метка показывает направление взгляда. Оранжевый — игрок Listen Server, синий — подключённый клиент.

## Поток данных

| Шаг | Где | Что происходит |
| --- | --- | --- |
| 1 | Клиент-владелец, `SendInput` | Считывает направление и рывок, присваивает последовательный `Sequence`, сохраняет в `pending` |
| 2 | Клиент, CSP включён | Немедленно выполняет `PredictionSimulation.Simulate` |
| 3 | `SubmitInputServerRpc` | Отправляет только `Sequence`, `Direction`, `Dash`; проверяет отправителя и данные |
| 4 | Серверный `FixedUpdate` | Один шаг за тик 1/30 с; сервер самостоятельно симулирует ввод и проверяет правила |
| 5 | `replicated` / NetworkVariable | Сервер публикует позицию, взгляд, ACK, кулдаун и результат рывка; клиентам запись запрещена |
| 6 | Клиент, `OnSnapshot` | Удаляет подтверждённые команды, восстанавливает полное состояние сервера, повторяет неподтверждённые предсказанные команды |
| 7 | Чужой клиент | Сглаживает изображение к авторитетной позиции |

`PlayerCommand` содержит `int Sequence`, `Vector2 Direction`, `bool Dash`. `MovementState` содержит номер подтверждённой команды, позицию XZ, направление взгляда, оставшиеся тики кулдауна, номер последнего рывка и код результата.

Клиент **не отправляет позицию, скорость, длительность шага или кулдаун**. Координаты Transform служат отображению. Серверная логика использует отдельный `authority`, поэтому локальная ошибка отображения не становится разрешённым серверным состоянием. `NetworkTransform` на игроке отсутствует: второй компонент записи позиции мешал бы reconciliation.

## Действие и серверные проверки

Ходьба — **5 единиц/с**, рывок — **4 единицы**, кулдаун — **90 шагов / 3 секунды симуляции**. Направление рывка берётся из ввода или последнего взгляда.

1. NGO проверяет владение ServerRpc; дополнительно проверяется `SenderClientId == OwnerClientId`.
2. Номер команды должен идти строго по порядку. NaN, Infinity и слишком длинное направление отклоняются.
3. Очередь сервера ограничена 240 командами, обработка — одна команда за FixedUpdate. Спам RPC не ускоряет игровое время.
4. Скорость фиксирована, направление ограничено единицей; диагональ не даёт ускорения.
5. Проверяются кулдаун, границы и весь путь рывка с радиусом персонажа 0,45. Недопустимый рывок отклоняется целиком.
6. Результаты: `1` — разрешён, `2` — отказ по кулдауну, `3` — отказ из-за стены/границы.

Обычная ходьба скользит вдоль осей при препятствии. Геометрия проверки статическая: граница X/Z ±10,5, стена X 1,5…2,5 / Z −2,5…2,5. Размеры объектов сцены соответствуют этим правилам. Если вручную перемещать стену в сцене, нужно изменить и константы в PredictionSimulation.

Кулдаун отсчитывается по обработанным командам; нейтральные команды тоже отправляются. При остановке доставки он может идти медленнее реального времени. Ускорить его отправкой множества запросов нельзя.

## Сравнение без CSP / с CSP

**Без CSP:** клиент сохраняет ввод и отправляет RPC, но применяет движение только после серверного снимка. Отложены и ходьба, и рывок.

**С CSP:** клиент сразу выполняет ту же симуляцию. При ACK восстанавливает серверное состояние **вместе с кулдауном и результатом действия**, затем повторяет ожидающие вводы. Сервер остаётся единственным источником окончательного состояния.

**«Отклик»** — программное время от постановки рывка в очередь ввода до локального результата или ответа сервера без CSP. **«Ответ сервера»** — время до получения результата действия и снимка, ACK которого покрывает команду. Это замеры приложения с точностью кадра/тика, не измерения задержки дисплея.

Каждый результат рывка отправляется владельцу отдельным надёжным `DashResultClientRpc`: при потерях NetworkVariable может объединять промежуточные снимки, но результаты дискретных действий не должны теряться. Замеры сопоставляются по номеру команды.

## Намеренное расхождение

Клавиша **F** ставит в очередь однократный ошибочный локальный рывок: игнорирует кулдаун/стену и увеличивает дальность в 1,8 раза. Флаг ошибки не передаётся серверу. Сервер получает обычный `Dash=true` и проверяет настоящие правила.

Для наглядного показа: профиль 175 мс / 4% на каждой стороне, CSP включён; Shift, затем через полсекунды F. Второй рывок недопустим из-за кулдауна. Клиент сначала показывает лишние 7,2 единицы, затем по серверному ACK восстанавливает допустимое состояние и повторяет более поздние вводы. В серверном состоянии ошибочного телепорта нет. Игрок может продолжать ходить после коррекции.

Автосценарий выполняет рывки примерно на 2-й и 2,7-й секунде. События CSV: `dash_input`, `server_dash`, `dash_confirmed`, `reconcile`. Снимки до/после: [docs/media/README.md](media/README.md). Числа проверки: [Prediction_Test_Matrix.md](Prediction_Test_Matrix.md).

## Эмуляция и запуск

| Профиль в меню | Настройка каждого узла | Базовый путь туда-обратно |
| --- | --- | --- |
| Без задержки | 0 мс, 0% | Локальная сеть + тики |
| 100 мс / 0% | `sendDelayMS=100`, `sendPacketLossPercent=0` | Не менее 200 мс + тики/очереди |
| 175 мс / 4% | `sendDelayMS=175`, `sendPacketLossPercent=4` | Не менее 350 мс + тики/повторные передачи |

`LabNetworkSimulator` создаёт `NetworkDriver` с `WithNetworkSimulatorParameters`. Надёжные RPC работают поверх задерживаемого UDP. При потере пакетов повторная передача увеличивает ожидание. Настройка применяется **до** запуска сессии; менять профиль нужно в меню **обоих окон**, затем переподключаться.

Сценарий показа и команды запуска: [README.md](../README.md). Автотесты: `python3 Tools/run_network_checks.py`, сборка: Unity → Practical 4 → Build macOS and validate simulation.

## Термины для защиты

- **Server authority:** только сервер определяет допустимое состояние.
- **Autonomous Proxy:** собственный персонаж на клиенте; собирает ввод и предсказывает.
- **Simulated Proxy:** чужой персонаж; показывает серверные обновления.
- **Saved Move:** неподтверждённая команда в `pending`, нужная для replay.
- **Client-Side Prediction:** показать ожидаемый результат до ответа сервера.
- **Server Reconciliation:** принять серверное состояние и повторить последующие вводы.
- **Network smoothing:** сгладить отображение чужого персонажа между снимками.

## Ограничения

Проверены два отдельных процесса на одном Mac. Предусмотрено 8 игроков, но нагрузочные проверки 8 игроков, Windows, внешняя сеть и Relay не проводились. Площадка плоская: без прыжков, гравитации и столкновений игроков. Коллизии — общая математическая геометрия, не произвольные Unity Collider.

Надёжные упорядоченные RPC выбраны для простоты: при потерях возможна очередь ожидающих пакетов. Для production понадобились бы пачки вводов и работа с пропусками. Список pending ограничен 240 вводами; при переполнении сессия останавливается. Некорректный номер команды отклоняется без автоматического восстановления злонамеренного клиента.

Сглаживание удалённых игроков — приближение к последнему снимку, без временного буфера интерполяции. Коррекция владельца видима специально для учебного показа. Долгая нагрузка не проверена; автоматические сценарии длятся 12 секунд на клиенте. Это минимальный учебный прототип.
