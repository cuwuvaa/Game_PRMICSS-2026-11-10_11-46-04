## Что проверяет скрипт

Оба процесса завершились штатно, клиент видит двух игроков, сервер обработал рывок удалённого игрока, ACK продвигаются и в конце проверки. Очередь всегда < 240, а среднее последних 6 замеров pending < 60 (две секунды ввода), после нейтрального ввода позиции совпадают. При 100 мс подтверждение >= 180 мс, без CSP отклик >= 180 мс, с CSP < 100 мс. При ошибке сервер отклоняет действие по кулдауну, клиент регистрирует исправление > 7 единиц и продолжает обмен. Проверено отсутствие исключений в runtime-логах.

| Тест | Последний ACK | Ожидающих вводов | Ошибка в конце |
| --- | ---: | ---: | --- |
| T1_lan | 353 | 2 | 0 по координатам CSV |
| T2_baseline | 349 | 7 | 0 по координатам CSV |
| T3_prediction | 347 | 8 | 0 по координатам CSV |
| T4_stress | 312 | 43 | 0 по координатам CSV |
| T5_correction | 329 | 29 | 0 по координатам CSV |

Задержка задаётся на отправке **каждого** узла. Надёжная доставка, тики и очереди добавляют время к базовым 200/350 мс туда-обратно. Потери случайны, числа одного запуска не являются средними. Pending в конце не обязан быть нулём: нейтральные команды продолжают отправляться. Клиент тестируется 12 секунд.

Замеры в таблице относятся к **первому разрешённому рывку**. В снимках T4/T5 может отображаться последующий отказ; сопоставляй по `seq` в CSV. Разница до 0,1 мс между близкими замерами связана с порядком чтения таймера.

Повторить: `python3 Tools/run_network_checks.py`. Перед проверкой пересобрать: Unity → Practical 4 → Build macOS and validate simulation. Сборка также проверяет 7 правил симуляции.
